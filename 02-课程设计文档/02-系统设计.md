## 1. 总体架构

系统采用 Flask 的**服务端渲染（MVC）**模式，浏览器只负责展示，所有业务逻辑在服务端完成：

```
┌────────────┐  HTTP  ┌──────────────────────────────────────────┐
│  浏览器    │ ──────▶ │  Flask 应用 (app.py)                    │
│  (模板渲染) │ ◀────── │                                          │
└────────────┘  HTML   │  ┌────────────┐   ┌──────────────────┐  │
                       │  │  路由层     │──▶│  业务逻辑层       │  │
                       │  │  @app.route │   │  参数校验/权限/    │  │
                       │  │  装饰器鉴权  │   │  库存扣减/违约金   │  │
                       │  └────────────┘   └────────┬─────────┘  │
                       │                            │ SQL        │
                       │  ┌────────────┐   ┌────────▼─────────┐  │
                       │  │  Jinja2     │◀──│  数据访问层       │  │
                       │  │  模板 10 个  │   │  sqlite3 + 参数绑定│  │
                       │  └────────────┘   └────────┬─────────┘  │
                       └────────────────────────────┼────────────┘
                                                    │
                                          ┌─────────▼─────────┐
                                          │  library.db (SQLite)│
                                          └───────────────────┘
```

### 分层职责

| 层次 | 承担者 | 职责 |
|------|--------|------|
| 表现层 | `templates\`（10 个 Jinja2 模板）+ `static\style.css` | 页面展示、表单提交、flash 消息渲染 |
| 控制层 | `app.py` 中 15 个路由函数 | 接收请求、权限校验、调用业务逻辑、选择模板 |
| 业务层 | `app.py` 中的工具函数与装饰器 | 表单校验、分页解析、权限判定、库存与违约金规则 |
| 数据层 | `get_db()` + 参数化 SQL | 建立连接、执行查询、事务控制 |

> **为什么把四层放在一个文件里？** 课程设计场景下，`app.py` 单文件 575 行带完整中文注释，
> 答辩时可以直接从上到下讲一遍，不必在多个文件间跳转。分层通过**注释分区标题**体现，
> 而不是通过文件拆分体现。

## 2. 技术选型

| 维度 | 选择 | 理由 | 被否的替代方案 |
|------|------|------|----------------|
| Web 框架 | Flask | 轻量、无额外概念负担、官方文档齐全 | Django 过重，课程设计用不到 |
| 数据库 | SQLite | 单文件即数据库、零配置、Python 内置 | MySQL/PostgreSQL 需要安装并配置服务 |
| 数据访问 | 原生 `sqlite3` | SQL 直接可读可讲，便于答辩解释查询逻辑 | SQLAlchemy 需先学一层抽象 |
| 模板引擎 | Jinja2 | Flask 默认集成，自动转义防 XSS | — |
| 前端 | 原生 HTML + CSS | 不引入框架，避免构建步骤 | Vue/React 需要 Node 环境与打包 |
| 密码存储 | `werkzeug.security` | 加盐哈希，Flask 生态标配 | 自实现易出错 |
| 测试 | `unittest`（标准库） | 零额外依赖即可运行 | pytest 需额外安装 |

**总体原则：除 Flask 外零第三方依赖**，`requirements.txt` 只有一行，环境搭建成本最低。

## 3. 模块划分

`app.py` 内部用注释分为 9 个功能区：

| 分区 | 内容 | 主要函数 |
|------|------|----------|
| 配置与常量 | 密钥、cookie 安全属性、业务参数 | — |
| 数据库 | 连接管理、建表、迁移、演示数据 | `get_db()` `close_db()` `init_db()` `_migrate()` |
| 工具函数 | 类型安全转换、输入清洗、分页 | `_to_int()` `_to_float()` `_clean()` `_page_args()` `_pager()` |
| 模板过滤器 | 金额格式化、空值占位 | `_money()` `_dash()` |
| 登录控制 | 两个权限装饰器、模板全局变量 | `login_required()` `admin_required()` `inject_user()` |
| 认证 | 注册、登录、退出 | `login()` `register()` `logout()` |
| 首页 / 仪表盘 | 统计与最近借阅 | `dashboard()` |
| 图书管理 | 检索、增删改查、表单校验 | `books()` `book_new()` `book_edit()` `book_delete()` `_parse_book_form()` |
| 读者管理 | 列表与注销 | `readers()` `reader_delete()` |
| 借阅 / 归还 | 核心业务 | `borrow()` `return_book()` `my_borrows()` `all_borrows()` |

### 关键设计决策

| # | 决策 | 说明 |
|---|------|------|
| 1 | **库存用条件更新而非先查后扣** | 避免并发下两人都通过"库存>0"检查导致超借，见第 4.3 节 |
| 2 | **读者注销用软删除** | `status` 字段标记，借阅凭证不丢失 |
| 3 | **图书删除要求零借阅记录** | 否则会产生指向不存在图书的孤儿记录 |
| 4 | **可借数由系统反推** | `available = total - 已借出数`，不接受手工填写，避免数据不一致 |
| 5 | **逾期判定下沉到 SQL** | 用 `julianday()` 计算，避免模板里字符串日期比较在格式变更后静默出错 |
| 6 | **会话密钥固定值** | 教学系统不部署生产，固定密钥保证重启后登录态不失效，便于演示 |
| 7 | **启动时初始化数据库** | `init_db()` 在模块导入时执行，`python app.py`、`flask run` 等启动方式均可 |

## 4. 关键业务流程

### 4.1 登录流程

```
POST /login
   │
   ├─ session 已有 user_id ──────────────▶ 302 → /dashboard
   │
   ▼
按 username 查 users
   │
   ├─ 无此用户 或 status != active ──────▶ flash「用户名或密码错误，或账号已注销」
   │                                       （统一提示，不暴露账号是否存在）
   ├─ 密码哈希不匹配 ────────────────────▶ 同上
   │
   ▼ 密码匹配
session.update(user_id, username, role, name)
   │
   └─▶ 302 → /dashboard
```

### 4.2 权限控制

两个装饰器按需组合，声明式地挂在路由函数上：

| 装饰器 | 判定条件 | 失败行为 |
|--------|----------|----------|
| `@login_required` | `session` 中存在 `user_id` | flash「请先登录」→ 跳 `/login` |
| `@admin_required` | `user_id` 存在 **且** `session.role == 'admin'` | 未登录跳 `/login`；非管理员跳 `/index` |

**权限分配**：图书增删改、读者管理、全馆借阅记录仅管理员；图书检索、借还、我的借阅对所有登录用户开放。

> 角色在登录时写入 session，整个会话期间不再回查数据库——性能好，代价是"改了角色需重新登录才生效"。
> 这在单管理员的教学场景下可接受。

### 4.3 借书流程（并发安全核心）

```
POST /borrow/<book_id>
   │
   ├─ 图书不存在 ────────────▶ 提示并返回列表
   ├─ 已借该书且未还 ────────▶ 提示「你已借阅该书且尚未归还」
   │
   ▼ 进入事务 with db:
   ┌─────────────────────────────────────────────────────┐
   │ UPDATE books                                       │
   │    SET available = available - 1                   │
   │  WHERE id = ? AND available > 0      ◀── 关键：条件更新│
   └─────────────────────────────────────────────────────┘
   │
   ├─ rowcount == 0（已被他人借空）──▶ raise ValueError → 回滚 → 提示库存不足
   │
   ▼ rowcount == 1（确实扣减成功）
   INSERT INTO borrows(user_id, book_id, borrow_date, due_date)
   │
   ▼
commit → 提示「借阅成功！请于 X 前归还」
```

**为什么不用"先 SELECT 查库存，再 UPDATE 扣减"？**

| 方案 | 并发 2 人借最后 1 本 | 结果 |
|------|----------------------|------|
| 先查后扣 | 两人都读到 `available=1` → 都通过检查 → 各自扣减 | `available = -1`，**超借** |
| 条件更新 | 数据库串行执行该 UPDATE，第二人执行时 `available > 0` 已不成立，`rowcount=0` | `available = 0`，**只有一人成功** |

条件更新的原子性由 SQLite 的写锁保证，无需应用层加锁。

### 4.4 还书流程

```
POST /return/<borrow_id>
   │
   ├─ 记录不存在 或 已归还 ────▶ 提示「借阅记录不存在或已归还」
   ├─ 非本人 且 非管理员 ──────▶ 提示「无权操作他人的借阅记录」
   │
   ▼ 进入事务 with db:
   overdue_days = 今天 - 应还日
   fine = max(overdue_days, 0) × FINE_PER_DAY
   │
   ├─ UPDATE borrows SET return_date=?, fine=?   WHERE return_date IS NULL
   ├─ UPDATE books   SET available = MIN(available + 1, total)
   │                                      ▲ 上限保护，防止数据异常时库存超过总册数
   ▼
commit → 有逾期则提示违约金，否则「归还成功」
```

### 4.5 分页流程

所有列表接口（图书、读者、我的借阅、全馆记录）共用同一套参数处理：

```
请求参数 page / per_page
   │
   ▼ _page_args()
   page    = max(1, 安全转整数(默认 1))          ← 非法输入回退，不抛异常
   per_page= clamp(安全转整数(默认 10), 1, 100)   ← 防止传入超大值拖垮服务
   offset  = (page - 1) × per_page
   │
   ▼
总数查询  ─┐
          ├─▶ _pager() ─▶ 生成 {page, pages, total, has_prev, has_next}
当前页查询 ─┘                    │
                                ▼
                  模板 _pager.html 渲染翻页控件
                  （自动保留当前筛选条件）
```

## 6. 页面与导航关系

```
登录页 /login ──注册──▶ 注册页 /register
    │
    ▼ 登录成功
控制台 /dashboard
    ├── 图书检索 /books ──借阅──▶ 我的借阅 /my ──归还──▶ 回到 /my
    │        └──(管理员) 新增 /books/new · 编辑 /books/<id>/edit · 删除
    ├── 我的借阅 /my
    ├──(管理员) 读者管理 /readers ──注销──▶ 回到 /readers
    └──(管理员) 借阅记录 /borrows ──筛选/分页──▶ 回到 /borrows
```

顶部导航栏按角色动态显示：读者只看到「首页 / 图书检索 / 我的借阅」，管理员额外看到「读者管理 / 借阅记录」。

## 7. 安全设计

| 威胁 | 防护措施 | 实现 |
|------|----------|------|
| SQL 注入 | 全部参数化查询 | SQL 中一律用 `?` 占位，用户输入不拼接进字符串 |
| XSS 跨站脚本 | 模板自动转义 | Jinja2 默认 `autoescape`；动态内容传给 JS 时用 `|tojson` |
| 会话窃取 | Cookie `HttpOnly` | `SESSION_COOKIE_HTTPONLY=True`，前端 JS 读不到 |
| 跨站请求伪造 | Cookie `SameSite=Lax` | 阻断大部分跨站 POST |
| 密码泄露 | 加盐哈希 | `generate_password_hash()`，库中无明文 |
| 暴力枚举账号 | 统一错误提示 | 不区分"用户不存在"与"密码错误" |
| 越权访问 | 双装饰器鉴权 | 服务端判定，不依赖前端隐藏按钮 |
| 未授权退出/提权 | 角色常量集中定义 | `ROLE_ADMIN` / `ROLE_READER` 消除字符串散落 |

**已知取舍**（答辩时如实说明）：未引入 CSRF 令牌机制、未强制 HTTPS、会话密钥为固定值——
三者均因本项目定位为**本地教学演示系统**，不面向公网部署。
